# Design

## Context

產品主檔模組（包含後端 `ProductController`、`ProductServiceImpl` 與前端 `templates/product.html`）目前存在以下需改進之處（詳細背景請參閱 `proposal.md`）：
1. 產品清單查詢預設以 `createdAt DESC` 排序，尚未依產品編號遞增排序。
2. 產品編號在新增時允許使用者自訂，未由系統統一配置。
3. 產品價格欄位允許小數點輸入，未強制整數單位。
4. 負責員工編號為一般文字輸入框，容易輸入不存在之編號且無主檔同步機制。
5. 表單輸入錯誤時之例外提示未明確指出問題欄位。

## Goals / Non-Goals

**Goals:**
- 產品主檔清單（後端分頁查詢與前端視圖）預設改依產品編號（`productId`）由小到大（ASC）依序排序。
- 新增產品時，產品編號由後端系統自動配置，前端表單設定為唯讀/禁用狀態；修改產品時維持唯讀。
- 產品價格以整數為單位：前端設定整數步進輸入，後端 DTO 驗證整數且不可為負數。
- 負責員工編號改為下拉式選單（`<select>`），非同步同步載入員工主檔資料（顯示姓名與編號）。
- 新增與修改產品時，拋出明確的欄位驗證例外，詳細告知使用者哪一項欄位輸入有誤（與員工模組驗證機制一致）。

**Non-Goals:**
- 不變更資料庫綱要（`product` 資料表欄位結構維持原狀，`price` 欄位維持現有資料型態，僅限制存入整數）。
- 不影響其他主檔模組（客戶、訂單）的現有功能。

## Decisions

### 1. 產品編號排序與自動配置
- **決策**：
  - 後端 `ProductServiceImpl.queryPage` 排序條件改為 `wrapper.orderByAsc(Product::getProductId)`。
  - 新增產品時，無論前端是否傳入編號，後端自動計算並生成格式為 `2026%02dA`（或依現有編號規則遞增）之唯一編號，並檢核防重複。
  - 前端新增與編輯彈窗中，`formProductId` 輸入框皆設為 `disabled`，新增時顯示提示「由系統自動配置」。
- **替代方案**：由前端生成編號或讓使用者自行輸入。
  - **評估**：易造成編號衝突且違反「系統配置，不提供使用者輸入」之業務規範，故採用後端自動生成。

### 2. 產品價格整數化檢核
- **決策**：
  - 前端 `<input type="number" step="1" min="0" id="formPrice">`，並在 JS 表單提交流程中以整數轉換處理。
  - 後端 `ProductDTO` 加入 `@Digits(integer = 10, fraction = 0, message = "產品價格必須為整數")` 與 `@DecimalMin(value = "0", message = "產品價格必須大於或等於0")`。
- **替代方案**：直接修改資料庫欄位為 INT。
  - **評估**：改動資料庫型態風險較高且非必要，透過 DTO 驗證與前端輸入限制即可達成整數單位目標。

### 3. 負責員工下拉選單與主檔同步
- **決策**：
  - 將 `templates/product.html` 中的 `formEmployeeId` 替換為 `<select id="formEmployeeId" class="select-control" required>`。
  - 前端於頁面載入或彈窗開啟時，非同步呼叫 `/api/employee/page?size=100`，過濾並載入在職或有效員工，選項格式為 `${employeeName} (${employeeId})`。
  - 編輯產品時，自動將下拉選單值設定為該產品原本的 `employeeId`。
- **替代方案**：使用自動完成（Autocomplete）輸入框。
  - **評估**：需求明確指定「提供下拉式選單，並同步員工主檔」，`<select>` 元素直覺、防呆效果佳且實作穩定。

### 4. 詳細欄位例外提示機制
- **決策**：
  - 後端利用 Spring Boot Bean Validation 與 `GlobalExceptionHandler`，若有欄位檢核失敗（如名稱為空、價格非整數或負數、庫存為負、負責員工為空），回傳 400 狀態碼與詳細錯誤訊息（如 `參數檢驗失敗: 產品價格必須為整數` 或 `負責員工編號不存在: xxx`）。
  - 前端在 `handleFormSubmit` 接收到錯誤時，若有具體欄位錯誤訊息，明確以提示或警告回饋給使用者，標示出具體欄位。

## Risks / Trade-offs

- **[Risk]** 員工主檔資料量較大時下拉選單載入延遲。
  - **Mitigation**：初始載入分頁大容量（如 100 筆）並快取員工清單，避免每次點擊重複發出請求。
- **[Risk]** 既有資料中若存在小數價格。
  - **Mitigation**：只針對新增與修改進行整數檢核，歷史資料查詢時可相容顯示或格式化。
